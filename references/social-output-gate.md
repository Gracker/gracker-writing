# 社交输出把关

X/Twitter、thread、小红书、社交总结、定时任务投到 Telegram 的可发布稿，交付前必须过这一关。平台结构跟对应 skill；文风、AI 味、升格和收尾跟本文件。

质检不通过就整段重写，不要只换词。

## Telegram 可发布稿

定时任务投到 Telegram 的社交正文，就是用户会全选、一键贴到社交平台的文字。必须完整，不能截成摘要再让人去翻落盘，也不能把 Obsidian 工作稿（status、今日精选、边界、本地路径）整份发出去。

1. 不要用 `账本` 这类黑话。原文不是在讲会计或 ledger，就写记录、清单、成本明细、证据清单。
2. 对看的人有用：事实、判断、链接都写进正文。不怕写长，怕写乱。有材料就写开，不要为了整齐压成提纲，也不要为交差堆一堆散点。没有值得发的内容，只写一句或保持安静。
3. 每段有顺序：发生了什么 → 数字/机制/取舍 → 判断 → 链接。一篇一个中心，不要在一段里跳题。
4. Telegram 里不要出现过程信息：落盘路径、status、评分、今日精选、可直接发布文案、备选短文案、任务信息、skill 名。

## 这一关在查什么

社交稿最容易写成「把 release note 整理得很干净」。词库扫描过不了关。下面这些过了禁用词检查，仍然算 AI 味。

## 失败即重写

命中任意 2 条，整篇重写，不要局部润色。

1. **changelog 综述**：开头先报版本，再把发布说明里的功能点并列铺开。读者读完只知道「出了这些功能」，不知道明天工作流改哪一步。
2. **否定开场**：`这条不是新闻` / `单独拿出来都不算` / `每一件都不算头条`。先否定一个没人坚持的判断，再给正文。
3. **升格包装**：`第一次被官方当一等公民` / `2026 年下半年做 X 的人手里多了一样东西` / `叠在一起才算一件事`。普通产品更新被写成阶段转折。
4. **目录预告**：`具体讲 N 个变化` / `一、二、三` 平行展开功能点。章节编号在长文里可以有，社交稿里这就是在念提纲。
5. **以前/现在 机械对仗**：连续两段以上都用「以前要……现在官方帮你做完」。一次可以，当骨架不行。
6. **工程位三件模板**：正文已经讲完，再补一组编号清单把同一判断再说一遍。清单只能新增动作，不能复读。
7. **口号收尾**：`真相不在 X，在 Y` / `官方替你做了第一刀` / `今天起这件事……`。听起来像金句，没有新的可执行信息。
8. **名人挂钩升格**：把同一天另一条不相干的名人帖接到产品更新上，制造「两件事对上了」的深刻感。来源没谈同一个对象，就不要硬接。
9. **可爱二元句**：`给方向不给答案` / `一等公民` / `缝给补了`。没有机制的俏皮话按填充删。

## 合格稿长什么样

- 第一句落到具体工作场景、命令、对话框或失败路径，不先给时代判断。
- 只展开会改变明天怎么干活的那一处；其余功能能省就省，preview 要标成 preview。
- 判断带边界：能用、先别写进稳定流程、clock domain / 裁事件 / 离线安装这类条件要写清。
- 结尾是今天能做的一步，或一句有条件的判断。不要金句。
- 同一对象用同一个名字。`trace_processor`、`Memscope`、`Memory Overview` 不要换称呼。

## 对照

不合格：

```text
Perfetto v58 今天凌晨出。

这条不是新闻——A、B、C、D——每一件单独拿出来都不算头条。但叠在一起，2026 年下半年做 Android 性能的人手里多了一样东西：跨设备的 trace 第一次被官方当一等公民处理。

具体讲三个变化。
一、……
二、……
三、……

性能问题的真相不在某一段，在跨段。今天起这件事官方替你做了第一刀。
```

合格方向：

```text
调手机和后端卡顿，两份 Perfetto trace 以前要对时间戳。v58 的 UI 能直接打开多个文件，合并对话框会标出哪些事件会被裁掉；CLI 走 `trace_processor util merge`，跨机器最容易踩的 clock domain 不一致，这条命令按 release note 是兜住的。

Memscope 和 Memory Overview 同日进 preview。smaps 快照出现在 trace 里时，Memory Overview 会自己打开。Memscope 先别写进稳定流程。
```

## 交付前 8 问

- 删掉版本号和功能名，还剩不剩一个具体工作变化？
- 有没有 `不是新闻` / `第一次` / `一等公民` / `真相不在`？
- 有没有 `具体讲 N 个` 或 `一、二、三` 功能并列？
- 有没有把不相干的名人帖接到产品更新上？
- 结尾是动作/边界，还是金句？
- preview / 裁事件 / clock domain 这类限制写了没？
- 换一个人看同一份 release note，会不会写出同一篇？会，就重写。
- 正文里有没有内部过程、路径、skill 名、质检报告？
- 用户能不能全选这段文字直接发到社交平台，而不用再删 status / 评分 / 落盘路径 /「今日精选」？
- 有没有把「账本」当成黑话用？原文不是在讲会计或 ledger，就改成记录、清单、成本明细或证据清单。
- 信息和判断是写进句子里的，还是贴在字段标签后面交差？链接在不在正文里？
- 是写乱了，还是写短了？乱（没顺序、没中心、散点堆砌）要重写；有内容的长稿不要为了整齐再压短。
